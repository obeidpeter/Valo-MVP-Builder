---
name: Valo doctrine decisions
description: Non-obvious design decisions for the Valo Bid Autopsy Workbench that future work must stay consistent with.
---

- **Reviewer identity is derived server-side, never trusted from the client.** Report sign-off and risk-override endpoints ignore any client-supplied `reviewerName` and instead use the authenticated local user's `name || email`. The request body still carries `reviewerName` because the generated client type requires it, but the server overwrites it.
  **Why:** the doctrine requires a *named human reviewer* for accountability; trusting a client string lets anyone attribute a sign-off to an arbitrary name.

- **There is no per-user project/client isolation, by design.** The schema has no user↔project membership table; `projects.reviewerId` is a single optional pointer. Any approved member (role ≠ `none`) can access every project. Routes gate on `requireMember` / `requireRoles(...)`, not on resource ownership.
  **Why:** it is a small private internal tool where all approved staff work across all packages. Do NOT add IDOR-style ownership checks expecting a membership model — there isn't one. "Isolation" in the spec means queries are scoped by `projectId` so data doesn't bleed between projects, which they already are.

- **Deterministic risk excludes AI-suggested items; the gate is a DENYLIST of unconfirmed states, not an allowlist of confirmed ones.** `computeRisk` counts only defects with `status === "open"` (excludes "suggested"/"remediated"/"waived"), and the missing/expired-evidence penalty applies only to non-suggested evidence rows (`RiskInput.evidence.suggested === false`) on mandatory requirements whose `reviewStatus` is NOT in `{suggested, rejected}` (see `UNCOUNTED_REVIEW_STATUSES`). So `pending`/`confirmed`/`edited` requirements DO count; only raw AI suggestions and rejected ones don't. Penalty is deduped per requirement. Both callers (`risk.ts`, `reports.ts`) must pass `e.suggested`.
  **Why:** doctrine = "everything is suggested until a named human confirms", so unconfirmed AI suggestions must not drive risk. BUT the sibling "risk-scoring/BOQ math" task owns the pending/confirmed scoring math and its tests treat `pending` mandatory requirements as counting — an allowlist of `{confirmed,edited}` collided with that (broke its tests). A denylist of `{suggested,rejected}` enforces the doctrine without redefining the sibling task's math. Requirement default `reviewStatus` is "suggested" (AI extract); manual POST creates "confirmed".
  **How to apply:** the doctrine seam is the explicit `suggested`/`rejected` states and the defect `open` status + evidence `suggested` flag — do NOT gate on "is it confirmed" (that steps on the scoring-math task). Proof harness: `artifacts/api-server/scripts/prove-ai-doctrine.ts` (`pnpm --filter @workspace/api-server prove:doctrine[:offline]`); unit coverage in `deterministic.test.ts`.

- **Risk `distribution` is serialised as `CountBucket[]` (`{key,count}`) at the route boundary**, even though `computeRisk` returns a `Record<Severity, number>` internally. The generated OpenAPI client expects the array shape.
  **How to apply:** any new consumer of the risk assessment must map the record→array at the edge, matching the OpenAPI contract.

- **`wordsToNumber` does NOT actually drop a spelled-out fractional part despite its docstring.** It only halts on a literal `cent`/`cents` token, so "one hundred dollars and fifty cents" returns 150 (the "fifty" is consumed as tens before "cents" breaks). Whole-number and currency-filler cases work correctly.
  **Why:** noted while writing unit tests; treated as existing behavior, not fixed, to keep the test task in scope. If a future task tightens `words_vs_figures`, fix the parser to drop the fraction and update the characterization test.

- **Deterministic-core unit tests live at `artifacts/api-server/src/lib/deterministic.test.ts`** and run via Node's built-in test runner through `tsx` (`pnpm --filter @workspace/api-server run test`), registered as the `test` validation command. No vitest/jest — imports must be extensionless so `tsc` typecheck also passes. NOTE: the two `routes/*.test.ts` files import `reports.ts` → `@workspace/db` at module load, so they fail with "DATABASE_URL must be set" when no DB is provisioned; `deterministic.test.ts` is pure and always runnable.

- **Audit events are a tamper-evident hash chain (FR-WFM-02).** `writeAudit` assigns a contiguous `seq`, links `prevHash → hash` (SHA-256 over prev hash + canonical JSON payload) under `pg_advisory_xact_lock(823914501)` in a `read committed`-pinned transaction with `SET LOCAL lock_timeout='2s'`/`statement_timeout='5s'` (a wedged lock degrades to a dropped audit event, never a stalled request); `createdAt` is app-generated ISO so the timestamp is covered by the hash. A unique index on `seq` is the fork backstop. Pure rules live in `lib/auditChain.ts` (unit-tested); the DB verifier is `scripts/verify-audit-chain.ts` (`pnpm --filter @workspace/api-server run verify:audit`).
  **Guarantee, stated honestly:** interior alteration/deletion/reordering is always detected; TAIL truncation is only detectable against an externally recorded head anchor — the verifier prints `HEAD seq=<n> hash=<hex>` each run and accepts `AUDIT_EXPECTED_HEAD="<seq>:<hash>"` to enforce it. Record the head outside the DB (runbook/CI log); do NOT store the anchor in the database (the threat model is DB write access). Unchained rows written after chain start are flagged via the DB-assigned `row_no` bigserial (not `created_at`, which an attacker can backdate).
  **How to apply:** never insert into `audit_events` except through `writeAudit` — seed.ts deliberately leaves the table empty so chains start clean at seq 1; do not re-add raw seed audit inserts.

- **Document intake computes a server-side SHA-256 manifest and FAILS CLOSED (FR-INT-02/FR-INT-01).** The intake route downloads the stored object once, hashes it, extracts text from the same buffer, and stores `size = buffer.length` (measured, never the client's claim). If the object can't be read back, intake is REJECTED (422 + `document.intake_failed` audit) — a document with no integrity baseline must not enter the corpus. The NDA gate is checked before AND re-checked after the slow download (mid-flight revocation), denials are audited (`document.intake_denied`) then 403. `POST /documents/:id/verify` distinguishes three outcomes with three audit event types: `integrity_verified`, `integrity_failed` (hash mismatch), and `integrity_unverifiable` (object unreadable — an availability problem that must never be recorded or displayed as tampering; the UI branches on `actualSha256 == null`). Client-supplied hashes are never trusted.

- **Provenance identifiers live in `lib/provenance.ts` only** (`ENGINE_VERSION`, `PROMPT_PACK_VERSION`, `MODEL_ID`); `llm.ts` and `docx.ts` consume them, and every generated report row + DOCX sign-off block is stamped with all three (NFR-AUD-01). Bump `PROMPT_PACK_VERSION` whenever any system prompt changes.

- **Fatal-block invariant (TRD I3 / FR-CSM-02): a report cannot be signed off while any OPEN fatal or likely-fatal defect exists — enforced in code with no override path.** `blockingSignOffDefects` (in `deterministic.ts`) is the single source of truth; the `/reports/:id/sign-off` route calls it and returns 409 + a `report.sign_off_denied` audit event before flipping status. Only `status === "open"` defects block — `suggested`/`remediated`/`waived` do not — deliberately mirroring `computeRisk`'s live-defect filter so the two deterministic checks can never disagree about what "open" means (there's a consistency test asserting an open fatal both blocks sign-off AND forces the critical band).
  **How to apply:** do NOT add an override/force flag to sign-off; the doctrine requires the block be unconditional. To sign off, the reviewer must first remediate/waive or downgrade the defect (an audited action). The frontend `reports-tab.tsx` surfaces the 409 `error` string via a destructive toast.
