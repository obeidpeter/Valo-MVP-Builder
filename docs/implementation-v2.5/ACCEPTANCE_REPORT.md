# Final acceptance and handover report

Report date: 2026-08-08
Overall status: **Not accepted as a complete production v2.5 platform**.

The candidate now contains material v2.5 tenancy, permission, release-governance and role-scoped UI work plus the source-controlled design/operations dossier. Focused backend and frontend verification passed. It is not deployed, and the remaining live-isolation, hostile-input, release-claim workflow, provider, package-integrity and operational evidence gaps prevent production acceptance. This status is intentionally conservative.

## Product and architectural decisions

Retain the deterministic-core/human-review doctrine and TypeScript/PostgreSQL/React/OpenAPI foundations. Evolve the modular monolith incrementally with organisation tenancy and PostgreSQL RLS, scoped permissions/break-glass, durable jobs/outbox, externally anchored audit checkpoints, provider adapters, server feature flags and effective-dated Nigeria/tender rule packs. Keep partner release, benchmarks, auto-confirm, payment charging and WhatsApp off until their separate gates pass. GCC remains deferred.

### Unresolved release blockers and material residual risks

- **Hostile upload enforcement:** request metadata has a 100 MiB absolute ceiling, deployments default to 50 MiB and document reads now enforce that limit while streaming. This reduces memory-exhaustion exposure, but signed upload length/type is not storage-bound and `lib/uploadInspection.ts` is still not wired for authoritative magic/MIME/malware/archive inspection or quarantine.
- **Request/job durability:** `middlewares/databaseTenancy.ts:22-57` holds the tenant transaction until response finish, so commit failure can occur after success is sent and slow external work consumes a pooled connection. Fire-and-forget extraction at `routes/documents.ts:204+` can outlive that request transaction. A durable job/outbox boundary is required.
- **Provider readiness and real delivery:** the evaluator at `lib/providerContracts.ts:109-129` is not invoked at server startup. Approved malware/OCR/payment/notification/licensed-feed/audit-anchor adapters and provider/storage E2E remain absent. Queued notification rows are not delivery proof.
- **Release-claim workflow completeness:** the gate in `routes/reports.ts:123-175` is read-side only: there is no application producer for `draftClaims`, evidence links or red-team runs/findings. Unsupported prose can therefore remain invisible to the registry, while the mandatory red-team result makes the normal release path unusable unless records are externally seeded. Direct DOCX/PDF routes at `reports.ts:501-597` check signed/latest state but do not rerun current governance such as later NDA revocation.
- **Governed decision workflow completeness:** `lib/defectGovernance.ts:74-136` and `lib/db/src/schema/index.ts:1225-1245` define a governed defect decision, but no route writes it. An open fatal defect therefore cannot be lawfully remediated or waived through the application. Payment and conflict decisions are similarly fail closed but operationally unavailable.
- **Immutable/reliable release package:** the project ZIP rechecks readiness under the project lock, but package/version/manifest/signoff/delivery tables at `lib/db/src/schema/index.ts:1489-1583` have no server lifecycle. `routes/reports.ts:835-856` marks the project exported and audits before archive finalization, so a failed stream can be recorded as exported without a delivered package.
- **Partner governance:** the least-privilege ceiling and client suspend/revoke lifecycle exist, but relationship ownership/QA rules, project scope and co-sign are not enforced end to end. Partner release remains denied.
- **Audit anchoring:** tenant-local hash chaining and verification exist; no independently immutable external anchor/adaptor proof exists.
- **Live acceptance evidence:** no live PostgreSQL/FORCE-RLS, provider, object-storage, migration, backup/restore/rollback, load, complete WCAG, security assessment or deployed smoke test exists.
