# Architecture glossary

**Current:** Terms reflect current source and governing documentation reviewed on 2026-08-31.

**Target:** Target-only terms are marked explicitly.

**Deployed:** A definition never proves that the named capability is enabled or deployed.

**Verified:** Use the linked contract/evidence for verification; this glossary is explanatory.

Last reviewed: **2026-08-31**

| Term                           | Meaning in Valo                                                                                                                                                                                                |
| ------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Access context                 | Server-derived organisation, membership/access source, roles, permissions, partner ceiling, and optional break-glass session applied to one request. It is not accepted from a request body.                   |
| Active v2 audit chain          | The current hash-chained tenant audit sequence begun at a recorded boundary from preserved legacy evidence. It does not claim the acknowledged legacy discontinuity was repaired.                              |
| Actor                          | The authenticated local user responsible for a request or recorded action. A worker actor requires a separate workload identity.                                                                               |
| Addendum                       | A new tender/source version whose effect is analysed against existing requirements, evidence, defects, responses, and release material; it never overwrites the source silently.                               |
| Approval                       | A named-human decision recorded only through a workflow that verifies current authority and exact source/version. A preflight, model output, flag, or client string is not approval.                           |
| Audit event                    | A content-minimised append-only record linked into the active tenant hash chain through governed writers.                                                                                                      |
| Audit witness / anchor         | An independent immutable/WORM checkpoint destination that makes tail rewriting detectable outside the primary database. This remains a target provider relationship.                                           |
| Break-glass                    | Time-bound, purpose-bound emergency access that is separately granted, selected, audited, and restricted. It is not a platform-admin tenant bypass.                                                            |
| Build                          | Compilation/bundling of source into artefacts. A build is neither a release candidate nor a deployment.                                                                                                        |
| Capability flag                | A server-evaluated, versioned activation decision scoped by environment/release/tenant/role/capability. UI flags may hide or explain a feature but never grant authority.                                      |
| C4 context/container/component | Architecture views at system, deployable/data runtime, and internal responsibility levels. Valo documents code-level detail through links rather than a C4 level-4 diagram.                                    |
| Canonical package              | The single governed `project_export` package aggregate for a project, with immutable/versioned manifests and a current version pointer.                                                                        |
| Client                         | A customer organisation or client record, depending on context. Architecture documents use “organisation” for the tenant authority boundary.                                                                   |
| Commit                         | A Git source snapshot. It becomes releasable only through the governed candidate and deployment process.                                                                                                       |
| `Current`                      | Present in the reviewed source tree/current contract. It does not mean deployed or activated.                                                                                                                  |
| Deletion certificate           | Evidence that the governed retention workflow met relational and storage terminal postconditions. A scan, request, detach, or provider attempt alone is not a certificate.                                     |
| `Deployed`                     | Bound to an immutable provider deployment and exact release evidence. A checked-in host configuration or “published” UI message is insufficient.                                                               |
| Direct membership              | Active membership of the selected organisation. Some high-risk workspaces intentionally reject partner-derived and break-glass access even when a synthetic permission appears similar.                        |
| Durable job                    | Reference-only background work with immutable scope, lease/fence, attempts, retry/dead-letter and cancellation semantics. The foundation exists; active worker execution remains gated.                        |
| Evidence                       | A governed record or artefact supporting a claim/requirement. “Evidence” in release documentation means a retained proof record, not the existence of code.                                                    |
| Exact export confirmation      | The POST export protocol binding the latest report and canonical package projection through an exact body, quoted scope hash, and UUID idempotency key.                                                        |
| Export scope hash              | SHA-256 over the exact report and package binding presented for export confirmation; it detects a changed projection between review and command.                                                               |
| External effect                | Communication, provider disclosure, payment, submission, deletion, or another action outside the authoritative Valo transaction. It requires explicit activation and reconciled evidence.                      |
| Fail closed                    | Deny or remain unavailable when identity, authority, input, configuration, provider, evidence, or state is missing/ambiguous, while preserving a safe recovery path.                                           |
| Idempotency key                | Client/worker-supplied stable request identity bound server-side to one exact operation scope. Reuse with changed input conflicts; exact replay returns the original durable result without duplicate effects. |
| Legacy audit discontinuity     | A known preserved gap in historical audit evidence. Valo records and verifies it separately rather than relabelling it continuous.                                                                             |
| Liveness                       | Dependency-free proof that the process can answer. It does not prove readiness, database controls, release identity, or business capability.                                                                   |
| Manifest hash                  | SHA-256 over canonical package manifest metadata and exact entry hashes/sizes/order.                                                                                                                           |
| Migration owner                | Privileged, startup/change-window database identity allowed to perform approved DDL. It is distinct from the application runtime role.                                                                         |
| Named human authority          | A current, identifiable person with a valid membership/grant/segregation relationship who performs the material decision. Models and automation do not inherit this authority.                                 |
| Organisation / tenant          | The immutable isolation and authorisation boundary applied to tenant-owned rows, storage metadata, jobs, retrieval, and audit. A client header may select but never invent it.                                 |
| Outbox                         | A durable intent committed with authoritative state so a later worker can attempt/reconcile an effect without losing the transaction boundary.                                                                 |
| Package version                | Immutable manifest/source-snapshot evidence for a particular canonical package generation. Render QA is a separate governed status.                                                                            |
| Partner-derived access         | Access inherited through an active client-partner relationship and bounded project/permission ceiling. It is not direct client membership.                                                                     |
| Preflight                      | Deterministic, explanatory evaluation of known blockers before a command. The authoritative command re-evaluates gates in its final transaction.                                                               |
| Production acceptance          | A bounded evidence console/recommendation. It records no deployment authority and cannot execute migration, backup, restore, rollback, or publish actions.                                                     |
| Provider adapter               | Typed boundary that normalises capability, error, timeout, retry/idempotency, health, privacy/region/retention, and reconciliation behavior for an external provider.                                          |
| Quarantine                     | State preventing uploaded material from entering ordinary processing/release until required inspection and reviewer controls clear it.                                                                         |
| Readiness                      | Authenticated proof that required lifecycle/database/release conditions allow the deployment to serve governed work. It is stronger than liveness and still not a business approval.                           |
| Release candidate              | Immutable API/Workbench artefacts, SBOM, manifest and source identity built by the controlled GitHub workflow from a full SHA already merged into `main`. It does not self-deploy.                             |
| Release identity               | Cryptographic identity derived from the candidate manifest and exposed/verified against a deployed runtime.                                                                                                    |
| Released project               | A project in `signed_off`, `exported`, or another protected release state where source mutation is denied except for exact governed command paths.                                                             |
| Restricted Mode                | Project/data posture that denies provider handling not approved for the required boundary. It cannot be waived by the browser.                                                                                 |
| RLS                            | PostgreSQL row-level security, enabled/forced as defence in depth for tenant-owned data. RLS is not identity authentication or a substitute for route permissions.                                             |
| Runtime role                   | Least-privilege database identity used by the API after startup, with no table ownership, superuser, `BYPASSRLS`, or general DDL authority.                                                                    |
| Schedule installation          | Provider/runtime configuration plus identity, receipts, liveness/alerts and operational ownership proving a declared job actually runs. A cron string in source is not installation.                           |
| Sign-off                       | Transactional transition binding a named current reviewer, exact report/project/source versions, readiness and segregation evidence.                                                                           |
| Source snapshot hash           | SHA-256 binding a governed output to the exact source/material state used to derive it.                                                                                                                        |
| Suggested state                | Non-authoritative AI/deterministic draft awaiting named-human review. It must not become a release fact merely because it parsed or scored.                                                                    |
| `Target`                       | Intended architecture or control not fully current/activated. Target status carries no implementation, deployment, budget, provider or acceptance claim.                                                       |
| Tenant transaction             | Request-scoped database transaction carrying a transaction-local current organisation and settling the governed request atomically.                                                                            |
| `Verified`                     | Supported by named retained evidence for a stated environment/scope. A source file or this glossary is not verification.                                                                                       |
| Workload identity              | Non-interactive, rotated identity for a worker/scheduler, distinct from a browser user and from database migration authority.                                                                                  |

For product terminology and UI statuses, also see the [user manual](../USER_MANUAL.md). For data conventions, see the [data model](../implementation-v2.5/DATA_MODEL.md).
