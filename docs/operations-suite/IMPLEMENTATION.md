## Persistence and security

- Project-operation envelopes are stored in the existing tenant-RLS `work_tasks` boundary with a reserved record prefix, closed schemas, size limits and compare-and-swap versions.
- Every non-read operations mutation appends a content-free tenant audit event in the same request transaction.
- First-pursuit onboarding progress is not browser storage: completed and reopened checkpoints form a policy-versioned, actor-scoped compare-and-swap stream in the tenant audit chain. A policy revision starts a new stream rather than rewriting historical receipts.
- Growth lead state is split deliberately: personal contact fields remain in `valo_intake`; the bulk operator queue receives only a company label and tender metadata. Assignment, SLA, reasoned disposition, conversion proposal/completion and contact-access receipts are recorded in the tenant audit chain without contact PII. The assigned operator's explicit handoff is transient and returns the selected contact's name plus only that lead's preferred channel value.
- The global pre-account queue is fail-closed unless `VALO_GROWTH_OPERATIONS_ORGANISATION_ID` identifies the one approved active internal Valo organisation. Lead locks are global to the intake request, so two tenant contexts cannot race the same status transition.
- Migration `0006_lead_operations_queue.sql` grants the runtime only the bounded active-queue read, closed status transition and single-record preferred-contact handoff functions. Assignment, role, purpose and optimistic-version checks remain in the tenant transaction before the handoff. Direct intake table access, bulk contact reads and purge execution remain denied.
- Both suites require the existing authenticated user, selected organisation, request-scoped tenant transaction and resource boundary. Partner-derived and emergency access do not expose Growth Operations.
- External effects remain `false` or manual throughout. There is no email, WhatsApp, CRM, calendar, issuer-portal, courier, submission, payment or model-provider call in these workflows.
